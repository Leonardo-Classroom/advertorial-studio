# 任務一：系統全面檢查報告

> 執行於 2026-08-09。靜態程式碼審查（10,772 行 Python，跨六個 app）
> ＋針對性動態驗證（`manage.py shell` 實測復現）。
> 每個發現標註嚴重度、觸發條件、影響、修法。

---

## 摘要

| # | 嚴重度 | 類別 | 標題 |
|---|---|---|---|
| 1 | 中 | 併發正確性 | `submit_rewrite` 排隊期間即蓋 `running`／`started_at`，會被誤判逾時 |
| 2 | 中 | 資源耗盡 | `runner.submit` 每個 run 無條件建執行緒、無建立上限 |
| 3 | 低 | 併發正確性 | `ensure_first_version` 有 race，併發建 v1 撞 `unique_together` → 500 |
| 4 | 低 | 效能 | `_acquire` 在 threading 鎖內做 DB 查詢 |
| 5 | 低 | 效能／可用性 | 語料關鍵字搜尋全表掃描，30 萬列需 ~39 秒 |
| 6 | 資訊 | 資料衛生 | `owner=None` 的孤兒資源前台永遠不可及 |

**整體評價**：核心安全面（XSS、SQL 注入、授權 scope）**紮實**，本 session 剛修過的
效能與一致性問題（深分頁、索引、版本鏡像、牆鐘保護）也都到位。剩餘問題集中在
**排程器的併發邊界**——都不是資料損毀等級，但在任務三的高並發負載下會浮現。

## 發現 1 ─ `submit_rewrite` 在排隊期間就標記為執行中（中）

**位置**：`studio/services/runner.py` `submit_rewrite()` vs `_work()`

`_work`（產稿）在**取得閘門之後**才蓋 `started_at`：

```python
def _work(run_id):
    _acquire()                      # 先排隊
    try:
        ...
        run.started_at = timezone.now()   # 真正開始才蓋章
```

但 `submit_rewrite`（重寫）在**丟進執行緒之前**就蓋：

```python
def submit_rewrite(run, base, feedback):
    run.status = "running"
    run.started_at = timezone.now()       # 排隊前就蓋章
    run.save(...)
    threading.Thread(target=_rewrite, ...).start()   # _rewrite 內才 _acquire()
```

**觸發條件**：閘門已滿（`max_parallel_runs` 個產稿正在跑），此時送出重寫。
該重寫的 thread 卡在 `_acquire()` 排隊，但資料庫裡它已經是 `running`、`started_at=現在`。

**影響**：
1. UI 顯示「產稿中」，實際上還在排隊——與產稿路徑的「排隊中（pending）」不一致。
2. 更嚴重：`reap_stale` 用 `started_at < now-45min` 判定逾時。若這個重寫在閘門
   後方排隊超過 45 分鐘（高負載下可能發生），會被 `reap_stale` 標記為 failed，
   即使它一秒都還沒真正跑。之後 thread 若終於取得閘門並完成，又會把狀態改回 done
   ——使用者會先看到「失敗」再變「完成」，且中間的 error 文字誤導。

**修法**：`submit_rewrite` 只設 `status`，把 `started_at` 的蓋章移進 `_rewrite`
取得閘門之後，與 `_work` 一致。或讓重寫也走 `pending`→`running` 兩段式。

## 發現 2 ─ 每個 run 立即建立一個執行緒，無上限（中）

**位置**：`studio/services/runner.py` `submit()`

```python
def submit(run):
    threading.Thread(target=_work, args=(run.pk,), daemon=True, ...).start()
```

`_active` 這個全域計數器搭配 `_gate` Condition **只限制同時「執行」的數量**
（`max_parallel_runs`），但**不限制執行緒的「建立」**。每次 `submit()` 都立刻
建一個 daemon thread；超出上限的那些卡在 `_acquire()` 的 `_gate.wait()`。

**觸發條件**：一個登入使用者連續／並發送出大量產稿請求（產稿 view 對此無節流）。

**影響**：N 個請求 = N 個執行緒。多數 parked 在 condition variable 上，各自持有
一份執行緒堆疊（Linux 預設 8MB）。1000 個排隊的產稿 ≈ 1000 個執行緒 ≈ 數 GB
記憶體 + 排程負擔。這是資源耗盡（DoS）向量，任務二會從對抗角度實測其上限。

**修法**：改用固定大小的工作佇列（有界 `Queue` + 固定數量的 worker），或在
產稿 view 端對「單一使用者同時 in_progress 的 run 數」設上限，超過就擋下並提示。

## 發現 3 ─ `ensure_first_version` 的建立競態（低）

**位置**：`studio/services/drafts.py` `ensure_first_version()` + `add_version()`

```python
def ensure_first_version(run):
    if run.draft_versions.exists():        # 檢查
        return run.draft_versions.first()
    text = first_text(run)
    ...
    return add_version(run, text, source="generate")   # 建立 version=1
```

`add_version` 沒有交易保護，而 `DraftVersion` 有 `unique_together = [("run","version")]`。

**觸發條件**：一個 run 剛完成的瞬間，`_work`（worker thread）呼叫
`ensure_first_version` 建 v1，同時使用者載入 `/drafts/<pk>/`（`draft_detail` view
也會呼叫 `ensure_first_version`）。兩者都通過 `exists()` 檢查（都看到還沒有版本），
接著都嘗試建 `version=1`。

**影響**：第二個 `create()` 撞 `IntegrityError`（unique_together），該請求 500。
時間窗很窄（run 完成與被檢視同時），但在任務三的並發輪詢下並非不可能。

**修法**：`add_version` 對 v1 的建立包 `transaction.atomic()` + 捕捉 `IntegrityError`
退回既有版本，或改用 `get_or_create`。

## 發現 4 ─ threading 鎖內做資料庫查詢（低）

**位置**：`studio/services/runner.py` `_acquire()`

```python
def _acquire():
    with _gate:
        while _active >= _limit():     # _limit() → SiteSettings.load() → DB 查詢
            _gate.wait()
        _active += 1
```

`_limit()` 每次都 `SiteSettings.load()`（一次 DB 查詢），而它在 `_gate` 鎖內、
且在 `while` 迴圈裡——每次 `notify()` 喚醒都會再查一次。

**影響**：持有 threading 鎖時做 I/O，並發喚醒時放大成多次查詢。`SiteSettings.load()`
有 pk=1 的快取但仍走 DB。非正確性問題，但在高並發下是不必要的鎖內 I/O。

**修法**：在進 `with _gate` 之前先讀一次 limit，或對 `SiteSettings` 加短期快取。

## 發現 5 ─ 語料關鍵字搜尋全表掃描（低）

**位置**：`corpus/views.py` `articles()`：`Q(title__icontains=q) | Q(body__icontains=q)`

`LIKE '%…%'` 前置萬用字元讓任何 B-tree 索引失效，30 萬列需逐列比對。實測：
只搜標題 26 秒、只搜內文 28 秒、合併約 39 秒。（列表排序本身已於本 session 修好，
從 29 秒降到 1 秒；這是搜尋路徑，尚未處理。）

**影響**：後台語料搜尋每次 ~40 秒；一個 staff 反覆搜尋可拖慢整台（SQLite 單寫）。
屬於效能／可用性問題，非資料風險。

**修法**：SQLite FTS5 全文索引（虛擬表 + 同步觸發器 + 一次性建索引），搜尋降到毫秒級。
獨立工程，本 session 已標記為待辦。

## 發現 6 ─ 孤兒資源（資訊）

有 3 個 `Brief` 與 286 個 `GenerationRun` 的 `owner` 為 `None`（早期實驗／批次產生）。
前台一律以 `owner=request.user` 過濾，所以這些在前台**永遠不可及**，只有後台
`/manage/` 列得出來。非 bug（設計上前台只顯示自己的），但值得知道：這類資料
只能從後台管理，且任務二確認過它們不會透過前台任何端點洩漏。

## 已驗證的正面項目

實測確認以下防線**有效**，非僅靠註解宣稱：

- **儲存型 XSS 全面擋下**。稿件內文與圖說都經 markdown-it（`html:False`、
  `linkify:False`）渲染：`<script>` 被逃脫、`<img onerror=>` 被逃脫、
  `[x](javascript:...)` 因 linkify 關閉連字面文字都不成連結。圖說端到端測試
  （`[[img:1|<script>...]]`）輸出 `&lt;script&gt;`，無未逃脫標籤。
- **無 SQL 注入面**。全專案無 `.raw()`／`.extra()`／手寫 `execute()`（除 WAL
  pragma 與受控的實驗指令），全走 Django ORM 參數化查詢。
- **`facts_version` 有 scope**。產稿 POST 用 `next(v for v in brief.fact_versions
  if str(v.pk)==wanted, versions[0])`，跨 brief 的 pk 比對不到會退回本 brief 最新，
  無跨資源 IDOR。
- **停用的風格指南擋在產稿入口**（`StyleGuide.objects.filter(is_active=True)`）。
- **本 session 剛加的牆鐘保護有效**：`_with_deadline` 在 client 逾時失效時仍能
  在期限+10 秒後放棄失控呼叫。
- **深分頁已修**（`paginate(related=...)`）、語料排序索引已補（29s→1s）、
  版本鏡像一致性已修。
