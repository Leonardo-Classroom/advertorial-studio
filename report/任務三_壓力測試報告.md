# 任務三：壓力測試報告

> 執行於 2026-08-09，本地後端（qwen3.6:27b + qwen3-vl:8b + bge-m3，共用單張 4090）。
> 分兩階段：第一階段真實 5 使用者並發全管線；第二階段隔離產稿排程器。
> 完整逐事件 log 保留於 `測試文件/stress_log.jsonl`、`測試文件/stress_phase2.jsonl`。

---

## 一句話結論

**產稿排程器（`max_parallel_runs=2` 閘門）在 10 個並發突發下完美守住上限 2；
但真正的瓶頸在它前面——事實抽取與圖片辨識完全沒有並發閘門，5 使用者並發時
事實抽取失敗率 96%，系統在到達產稿之前就崩潰。**

---

## 第一階段：5 使用者並發全管線（真實負載）

**設計**：5 個帳號（stress1-5）同時啟動，各依序做 5 個專案（共 25），
每專案跑上傳解析 → 事實抽取 → 圖片辨識 → 產稿的完整管線。

**結果**：

| 指標 | 值 |
|---|---|
| 建立專案 | 25 / 25（上傳解析全部成功，2.6-10.1s） |
| 事實抽取成功 | **1 / 25（4%）** |
| 事實抽取失敗 | **24 / 25（96%）**，皆在 ~252-261s 逾時 |
| 圖片辨識 | 1（唯一成功的專案，但因競態選到 0 張，見附註） |
| 產稿完成 | 1（唯一走到這步的，耗時 **422 秒**——被並發抽取拖慢） |
| 總牆鐘時間 | 25.6 分鐘 |
| 錯誤（例外） | 0（全部乾淨失敗，無崩潰） |

**失敗機制（關鍵發現）**：

```
Ollama 設定 OLLAMA_NUM_PARALLEL=1 → 一次只處理一個推論請求。
5 個並發事實抽取 → 1 個在跑，4 個在 Ollama 佇列排隊。
每個事實抽取的 client timeout = 240s（extract_facts）。
第 5 個要等前 4 個各跑完（每個 ~85s）≈ 340s > 240s → 逾時。
於是每 5 個並發只有 1 個成功，其餘逾時 → 96% 失敗。
```

Ollama log 佐證：失敗的請求記為 `500 | 4m0s`（client 在 240s 放棄後 Ollama 端的紀錄）。

**架構缺口**：事實抽取（`ingest_runner`）與圖片辨識（`classify_checked`）
**沒有任何並發閘門**——只有產稿（`runner`）有 `max_parallel_runs=2`。所以
並發上傳直接淹沒 Ollama。這是本次壓測揭露的**最重要問題**。

---

## 第二階段：隔離產稿排程器

第一階段崩得太徹底，產稿排程器幾乎沒被測到。第二階段先循序建好含事實的專案，
再一次並發送出 10 個產稿，隔離觀察 `max_parallel_runs=2` 閘門。

**閘門行為（核心結果）**：

| 指標 | 值 |
|---|---|
| 送出 | 10 |
| 閘門上限 | 2 |
| **實測最大同時執行** | **2** ✅ |
| **閘門是否守住** | **是** ✅（全程 running=2、pending=8，維持逾 5 分鐘穩定） |
| 產稿完成 | 8 |
| 產稿失敗 | 2 |

**排隊時間**（`created_at`→`started_at`），完美反映 gate=2 的序列化：

```
run 516, 517: 排隊 0.4s（立即取得 2 個空位）
run 518, 519: 排隊 640s（等前 2 個結束）
run 520-525: 排隊 868 / 900 / 929 / 952 / 987 / 1013s（逐波往後）
```

**執行時間揭露「暖機效應」**：

```
run 516, 517（首波，冷模型）: 640s → 逾時失敗
run 518, 519（過渡）:          228s, 258s → 成功
run 520-525（模型暖機後）:     51-62s → 成功
```

首波兩個在冷啟動 + bge-m3 嵌入模型與 27B 文字模型搶 VRAM 抖動下跑到 640s 逾時；
模型暖機、VRAM 穩定後，同樣的產稿只要 ~50 秒。

---

## 綜合發現

### 1.（高）事實抽取／圖片辨識無並發閘門 → 並發下崩潰

只有產稿有 `max_parallel_runs` 閘門；事實抽取與圖片辨識沒有。5 使用者並發時，
事實抽取失敗率 **96%**。這是任務一發現 2、任務二排程 DoS 的真實負載版本。

**修法**：對事實抽取與圖片辨識也加並發閘門（可與產稿共用同一個 `_gate`，
或各設一個 limit=1-2 的閘門）。**閘門的真正價值不只是省算力，而是讓 Ollama 的
佇列夠淺、請求不致排隊逾時**——第二階段證明：產稿有閘門（佇列 ≤1 個等待）→
暖機後幾乎全成功；事實抽取無閘門（5 個堆疊 4 個等待）→ 96% 逾時。

### 2.（資訊，正面）產稿排程閘門本身正確無誤

`max_parallel_runs=2` 在 10 個突發下全程守住 2，排隊時間精確反映序列化。
排程器的核心邏輯沒有問題。

### 3.（中）本地事實抽取的 240s 逾時對大輸入太緊

第二階段的**循序**（無並發）事實補建 3 次也全在 252s 失敗。三檔案專案的
`raw_text` 約 20k 字，冷啟動 27B + Qwen3.6 思考模式尾端延遲，單次就可能超過 240s。
建議把事實抽取的 `timeout` 從 240s 拉高（如 400s），或先暖機模型。

### 4.（中）冷啟動 + VRAM 抖動放大延遲

閒置後首次產稿 640s、暖機後 51s，差距 12 倍。bge-m3 嵌入模型與 27B 文字模型
共用 24GB 卡、輪流換入換出是主因。生產環境若走本地，應考慮：嵌入改線上、
或把文字模型的 `num_ctx` 壓小以留 VRAM 給嵌入常駐。

### 5.（正面）牆鐘保護生效，系統自我恢復

本 session 上一個 commit 加的 `_with_deadline` 在本次壓測中**反覆生效**：
所有卡住的請求在期限後乾淨失敗（`ModelTimeout`），而非永遠佔住執行緒。
25 個第一階段專案 + 10 個第二階段產稿，**0 例外、0 永久卡死的 `processing`**，
測後執行緒回落至基準（無洩漏）。若沒有這道保護，第一階段的 24 個逾時會全部
無限期掛住。

### 6.（觀測）峰值負載下整台機器降級

峰值時連 `ps aux`、`ollama ps` 都逾時（>120s）——GPU 100% + OneDrive 掛載的
`db.sqlite3` 在 WAL 寫入競爭下，整台機器 IO 明顯降級。這是單機、單 GPU、
資料庫在網路磁碟上的綜合結果，非單一程式 bug，但說明本地部署在高並發下的脆弱。

## 附註：協調器的一個小競態（非系統 bug）

第一階段唯一成功的專案（stress4-p1）圖片辨識選到 0 張。原因是測試協調器在
`fact_versions.exists()` 一為真就去選圖，但 `image_service.ingest` 在
`_extract_facts_and_images` 裡是**事實版本建立之後**才跑的——存在「事實已就緒
但圖片尚未入庫」的短暫窗口。這是測試腳本的競態，不是系統缺陷；但也提示
「事實就緒」與「圖片就緒」是兩個不同的時間點，前台若有依賴需注意。

---

## 建議修補優先序

1. **（高）為事實抽取與圖片辨識加並發閘門**——這是並發崩潰的根因，
   也同時堵住任務二的排程 DoS。
2. **（中）拉高事實抽取 timeout**（240s→400s）或暖機模型，降低單次失敗率。
3. **（中）緩解 VRAM 抖動**：嵌入改線上，或壓小文字模型 num_ctx。
4. 產稿排程閘門無需改動（已驗證正確）。
