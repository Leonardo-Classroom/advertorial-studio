# 任務二：資安檢查與滲透測試報告

> 執行於 2026-08-09。對自有系統的授權滲透測試，以 Django test client
> （含 `enforce_csrf_checks`）實際發動，非破壞性為原則。每項記錄手法、預期、
> 實際結果、是否成功、修法。測試帳號與資料測後已清除。

---

## 摘要

| 類別 | 結果 | 嚴重度 |
|---|---|---|
| IDOR 越權存取（15 端點） | **全數防禦**，皆 404、無洩漏、受害者資料未變 | — |
| 認證邊界（未登入） | **全數導向 login** | — |
| 授權邊界（非 staff 存取後台） | **全數擋下**（導回 home + 提示） | — |
| CSRF（fetch 端點） | **強制**，無 token 皆 403 | — |
| SQL 注入 | **免疫**（ORM 參數化，DROP TABLE 無效） | — |
| 儲存型 XSS | **免疫**（見任務一，markdown-it `html:False`） | — |
| 隱藏欄位竄改 | **無效**（伺服器不信任 POST 的敏感欄位） | — |
| 檔案上傳：格式偽裝／路徑穿越／副檔名 | **防禦得當** | — |
| **檔案上傳：無大小上限** | **有缺口** | 中 |
| **排程 DoS：執行緒無上限建立** | **可利用** | 中-高 |

**結論**：認證、授權、注入、XSS 四大面向**紮實無破口**。兩個真實缺口都屬
**資源耗盡（DoS）**類，需登入才能觸發，不涉及資料外洩或越權——但在多使用者
環境下應修補。

---

## 一、IDOR 越權存取 ─ 全數防禦 ✅

**手法**：建 `sec_victim`（受害者）與 `sec_attacker`（攻擊者）兩帳號，受害者
擁有一個含機密事實與稿件的專案，攻擊者以受害者的 `brief_id`/`run_id`/`file_pk`
逐一打**所有** 15 個帶 pk 的端點。

**結果**（全部 HTTP 404、無「機密」字樣洩漏、受害者資料零改動）：

```
GET  brief_detail / upload_status / images_progress / draft_detail
     / draft_status / draft_download                    → 全 404
POST rename / facts_edit / facts_update / primary_kol
     / generate / upload_retry / file_retry / draft_edit
     / draft_revise                                     → 全 404
受害者 brief.title 未變、facts 版本數 1、run 版本數 1、attacker 未產生任何 run
```

**原因**：每個 view 一律經 `get_object_or_404(_my_briefs(request), pk=pk)` 或
`_my_runs(request)`（皆 `owner=request.user` 過濾）。連接關係也 scope
（`brief.source_files`、`brief.runs.filter(owner=...)`）。**無單一遺漏**。

---

## 二、認證與授權邊界 ─ 全數正確 ✅

- **未登入**存取 `/`、`/drafts/`、`/upload/`、`/briefs/<pk>/`、`/manage/*`
  → 一律 `302 → /login/?next=...`。
- **一般使用者（demo）**存取 `/manage/`、`/manage/corpus/`、`/manage/runs/`、
  `/manage/advanced/`、`/manage/users/`、`/manage/briefs/` → 一律 `302`，
  導回 `portal:home` 並顯示「這個頁面僅限管理者使用」（`staff_required`
  刻意不導向 login，避免「已登入卻被要求再登入」的錯覺）。

---

## 三、CSRF ─ 強制 ✅

以 `enforce_csrf_checks=True` 的 client 對 fetch 端點送 POST（無 token）：

```
POST /briefs/<pk>/rename/          → 403
POST /manage/corpus/guides/<pk>/toggle/ → 403
```

這兩個是本 session 新增的 fetch 端點，都在無 token 時正確拒絕。（其餘 fetch
端點——圖片核准、圖說儲存、facts 自動儲存——共用同一套 Django CSRF middleware。）

---

## 四、注入 ─ 免疫 ✅

**SQL 注入**：對語料搜尋送
`' OR 1=1`、`'; DROP TABLE corpus_article;--`、`%`、`_`、`UNION SELECT` 等
→ 全部 HTTP 200，`corpus_article` 資料表完好。Django ORM 的 `icontains`
一律參數化，注入字元被當成字面搜尋內容。

**XSS**：見任務一——稿件內文與圖說經 markdown-it（`html:False`、`linkify:False`）
渲染，`<script>`／`<img onerror>`／`javascript:` 全部失效。

---

## 五、登入狀態下的惡意操作 ─ 全數擋下 ✅

- **以停用的風格指南產稿**：`generate` view 用
  `StyleGuide.objects.filter(is_active=True)` 擷取，停用的 guide → 404。
- **竄改 `exemplar_count`／`max_rewrites`**：這些欄位在 view 內一律取自
  `SiteSettings.load()`，**完全不讀 POST**，塞 `9999` 無效。
- **跨 brief 的 `facts_version`**：`next(v for v in brief.fact_versions if
  str(v.pk)==wanted, versions[0])`，別的 brief 的 pk 比對不到 → 退回本 brief
  最新版，無法用他人的事實產稿。
- **越權改名**：`brief_rename` 經 `_my_briefs` 過濾 → 他人專案 404（見 IDOR）。

---

## 六、檔案上傳 ─ 大致安全，一個缺口 ⚠️

**防禦得當的部分**（實測）：
- **格式偽裝**（純文字改名 `evil.pptx`）：`python-pptx` 拋 `PackageNotFoundError`，
  該來源檔標記 `failed`，**未當機、未執行任何內容**。安全失敗。
- **路徑穿越檔名**（`../../../etc/passwd.pdf`）：Django storage 消毒為
  `briefs/passwd.pdf`，未逸出 media 目錄。
- **不支援副檔名**（`.exe`）：`format_for` 直接 `ValueError` 拒絕。

**缺口 ─ 無上傳大小上限（中）**：
- `DATA_UPLOAD_MAX_MEMORY_SIZE`（2.5MB）只限制**非檔案**表單欄位；檔案上傳
  串流到磁碟，**本專案未設任何總量上限**。
- 一個登入使用者可上傳超大「.pptx」耗盡磁碟；更危險的是 **zip bomb pptx**
  （pptx 本質是 zip），`extract_images` 會解壓所有內嵌媒體，精心構造的
  壓縮炸彈可在解壓階段耗盡記憶體。
- **修法**：在 view 或 middleware 對單檔／單批次設大小上限（例如單檔 200MB），
  並在 `extract_images` 對解壓後總量設上限（解壓炸彈防護）。

**✅ 已修復（2026-08-09）**：`source_extract.check_upload()` 在 `create_brief`
建立任何東西之前逐檔檢查，四個上限都可由 `.env` 調整——單檔 200MB、單批 600MB、
解開後總量 2GB、壓縮比 200:1。實測：自製壓縮炸彈（1019KB 宣稱解開 1.0GB、
比 1029:1）擋下；超過單檔上限擋下；批次超量擋下；被拒的上傳不會留下任何 Brief；
124MB 的真實簡報照常通過；假冒 pptx 的純文字仍交給 parser 安全失敗，不在此重複報錯。

壓縮炸彈的檢查只讀 zip 中央目錄裡**宣稱**的大小，不做解壓，所以成本為零——
這擋得住標準炸彈（它的手法就是宣稱數 GB），但那些數字是造檔者寫的，不是保證。
單檔位元組上限是不依賴這些數字的後盾。

## 七、排程 DoS ─ 可利用（中-高）⚠️

**手法**：以 stub 取代真正的產稿（不碰 GPU），單一使用者連續送出 40 個產稿請求，
量測執行緒數。

**結果**：

```
max_parallel_runs = 2
送出 40 個產稿請求後：
  執行緒數：1 → 41（淨增 40）
  runner._active（實際並行執行）：2（受閘門限制）
  仍 pending（排隊中）：40
```

**分析**：`max_parallel_runs` 的閘門（`_gate` Condition + `_active` 計數）
只限制**同時執行**的數量（正確地限在 2），但**不限制執行緒的建立**——
`runner.submit()` 每個 run 都無條件 `threading.Thread(...).start()`，超出上限的
38 個 parked 在 condition variable 上。且**產稿端點對單一使用者同時 in_progress
的 run 數毫無節流**。

**影響**：N 個請求 = N 個執行緒，各持一份堆疊（Linux 預設 8MB）。數千個排隊的
產稿 ≈ 數 GB 記憶體 + 排程負擔，可拖垮行程。這是任務一發現 2 的可利用證明。

**修法**（擇一或並行）：
1. 產稿 view 端對「單一使用者同時 in_progress 的 run 數」設上限（例如 3），
   超過就擋下並提示——最小改動、直接堵住濫用。
2. 排程改用有界 `Queue` + 固定數量的常駐 worker，取代「每個 run 一條執行緒」。

（此缺口也是任務三真實負載測試的觀測重點之一。）

**✅ 已修復（2026-08-09）**：採用修法 2。`studio/services/runner.py` 改為深度 100
的有界佇列加上最多 `max_parallel_runs` 條 worker。以本節同樣的手法重測——
送出 120 個產稿請求，只起 **2 條執行緒**（舊版會是 120 條），佇列滿之後多的 18 筆
當場被拒絕並提示使用者，不再無聲堆積。

**殘留**：佇列是全域的，所以修法 1（單一使用者同時 in_progress 上限）仍未實作——
一個使用者仍可獨自佔滿 100 個位子，把其他人擋在門外。這已不是資源耗盡
（記憶體不再隨請求數成長），而是公平性問題；真正的解法是依使用者輪流取件，
而非只設上限。
