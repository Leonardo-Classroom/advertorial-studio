> 2026-08-12。這**不是**一份模型比較報告——雖然它原本要是。
>
> 240 篇的產稿全部執行了，但**只有 11 篇完成評分**：評審走 OpenAI，而額度在
> 評分階段一開始就用完了。品質比較因此無法成立，這份文件記的是**速度、穩定度，
> 以及三個值得記住的失敗**。
>
> 品質數據待補：165 篇成功的稿都還在資料庫裡，**只要重跑評分、不必重新產稿**。

## 設計

| 項目 | 值 |
|---|---|
| 風格指南 | `#26 COOL-STYLE`（24 篇樣本）|
| 專案 | 十個**不同的**專案：198–201、206–208、177、166、164 |
| 方案 | A（single）與 B（staged）|
| 重寫 | `max_rewrites=1` |
| 評審 | `gpt-5.6-sol`（effort=high）|
| 併發 | 三家 API 各自一個行程、各 10 併發＝**總計 30 併發** |

三家並行需要端點層級的覆寫。`SiteSettings.online_provider` 是進程全域的，
所以在此之前兩個批次會互相覆蓋設定；`compare_models` 新增的
`--provider` / `--judge-provider` 讓每個執行緒帶自己的端點，三家才真正同時跑。
實測三家同時發出，總牆鐘等於最慢那家（15.2 秒），不是三者相加。

### Kimi 慢一個量級，這次有樣本了

先前只有單次測試（15 秒回一句話），現在有 25 篇：**`kimi-k3` 方案 A 要 759 秒、
方案 B 要 1426 秒**，而最快的 `gpt-5.4/A/off` 只要 68 秒——**相差 11 到 21 倍**。

這不是網路波動。`kimi-k3` 的重寫階段中位 480 秒，單這一段就比多數組合的總時
還久。Kimi 的思考模式**關不掉**（試過各種參數形狀），所以推理時間是固定成本。

### 推理強度對時間的影響，在這批更明確

同模型同方案，只切換強度：

| 組合 | off | high | 倍率 |
|---|---:|---:|---:|
| deepseek-v4-pro / A | 91.6s | 266.0s | **2.9×** |
| deepseek-v4-pro / B | 191.1s | 376.2s | 2.0× |
| gpt-5.6-sol / A | 138.2s | 204.8s | 1.5× |
| gpt-5.6-sol / B | 181.9s | 406.0s | **2.2×** |
| deepseek-v4-flash / A | 209.1s | 166.8s | **0.8×** ⚠️ |

最後一列是反的——`deepseek-v4-flash` 開了 high 反而**比較快**。這一點提醒：
`--thinking high` 對 DeepSeek 而言只是「不送停用參數」，也就是它的預設行為；
所謂 off/high 在 DeepSeek 上是二元開關，而它的預設本來就會思考。這個 0.8 倍
多半是時段波動，不是「思考讓它變快」。

### 方案 B 一律比方案 A 慢

八組可比對的配對全部如此，慢 1.1 到 1.9 倍。這與先前兩份報告一致。

## 三、三個值得記住的失敗

### 1. 沒先確認餘額就跑 240 篇

技術上驗證了三家可以並行，卻沒有先估算 240 篇（含重寫、其中 80 篇 high 強度）
要花多少額度。**先跑一個小批次探路**，或先查餘額，就能避免 75 篇的浪費。

### 2. 一個報告的格式錯誤差點毀掉整批資料

`compare_models` 原本先產摘要、再寫 JSON。當有稿件未完成評分時，
`statistics.median` 撞到 `None` 而拋出 `TypeError`，整個指令崩潰——
**80 篇已經跑完的 OpenAI 資料因此沒有寫進檔案**。

已修：**JSON 先寫、摘要後產**，而且摘要會跳過未評分的列並標明缺了幾筆。
一次跑掉的時間與金錢，不該輸給一個格式化錯誤。

（這批資料最後是從 log 逐行解析救回來的——240 筆產稿紀錄全數還原。）

### 3. 評審與候選共用一個額度池

評審是 `gpt-5.6-sol`，候選裡也有 OpenAI 模型。額度用完時，**產稿和評分一起停**，
所以連「已經產好的稿」都評不了。下次應該讓評審用獨立的供應商，或至少
**先把評分的額度預留下來**。

## 四、如何補完品質數據（成本很低）

165 篇成功的稿件都還在資料庫裡（`style_guide_id=26`）。要拿到品質比較，
**只需要重跑評分，不必重新產稿**——那省下的是絕大部分的成本。

```bash
# 充值後，用最終評審重評（約 330 次呼叫）
python manage.py compare_models ...   # 或用重評腳本針對既有 run
```

需要的前置：

1. **OpenAI 充值**（評審用）。
2. **Kimi 充值**，否則 `k2.7-code` 兩個模型完全沒有資料，
   `k2.6` 也只有 8 篇。
3. 決定評審要不要換成不參與比較的供應商——目前 `gpt-5.6-sol` 同時是候選之一。
