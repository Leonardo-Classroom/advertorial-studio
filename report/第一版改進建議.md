## 一、逐項分析

### ① 待確認事項：加編號、下方給輸入欄

> **原文**：這幾處系統不確定，請你確認：這個列點，並註明請依數字更新，下方放個輸入欄
> 讓人輸入更新，現在請 GPT 問使用者問題再回答也是同樣的條列式，就不用再教育使用者了。

**現況**
`templates/portal/brief_detail.html:15-22` 把 `facts["uncertain"]` 當成唯讀清單顯示，
沒有編號。使用者要更正，只能去右邊那個 JSON 文字框自己找位置改。

**建議**
清單加上數字編號，下方放一個文字框，讓使用者用「1. …／2. …」的格式回答。
這個互動模式與 ChatGPT 的問答一致，確實不需要額外教學。

**待你決定** —— 答案怎麼回寫進系統？

| 做法 | 優點 | 缺點 |
|---|---|---|
| A. 只當補充說明，附在提示詞後面，不動 facts | 零風險，最快 | 事實覆蓋率檢查看不到這些內容 |
| B. 用 LLM 把答案合併進 facts，並顯示前後差異讓使用者確認 | 事實結構保持完整 | 多一次 API 呼叫（約 NT$1.6），LLM 可能改錯 |

我傾向 **B 但一定要有差異確認畫面**。理由是這些待確認項目往往正是品牌名、型號這類
**必須逐字出現在稿件裡**的資訊；若走 A，它們不會進入 `required_fact_values()`，
系統就無法驗證稿件有沒有寫到，等於少了一道防線。

### ② 抽出的內容：改成文字敘述、不給直接編輯

> **原文**：非程式人員會看不懂，最好僅以文字敘述。並且不要讓使用者直接更動，
> 一樣下方放個更新欄位。

**現況**
`brief_detail.html:38-45` 直接把 facts 的 JSON 塞進 `<textarea class="mono">`，
420px 高，可直接編輯。這確實是給工程師看的東西，意見完全正確。

**建議**
1. 前台改成分區塊的可讀敘述（品牌、產品、必提詞、合作人選、活動資訊…），
   `internal_only` 整段不顯示——反正系統本來就不會把它寫進稿子。
2. 移除 JSON 編輯框，改為唯讀。
3. 下方放「要更正什麼？」文字框。
4. **後台維持 JSON 編輯**，那是管理者除錯用的。

**待你決定** —— 與 ① 是同一個技術問題

①②都需要「自然語言 → 結構化事實」的更新路徑。**這是整次改版最大的技術風險**，
建議兩項合併成同一套機制，不要各做各的。第三個選項是：

| 做法 | 優點 | 缺點 |
|---|---|---|
| C. 不用自由文字，改成一格一格的表單（品牌□ 產品□ 必提詞□…） | 完全不靠 LLM，改錯不可能 | 與「下方放個更新欄位」的原意不同；欄位多時仍嫌繁瑣 |

C 最安全，但偏離意見書的原意。要選 C 的話請直說。

### ③ 一頁兩張圖怎麼處理

> **原文**：確認可用圖片：一頁有兩張圖怎處理為佳？

這是問句，不是指示，所以先回答。

**現況**
`BriefImage.slide_index` 已經記錄了頁次（`briefs/models.py:154`），
所以「哪幾張來自同一頁」系統是知道的，只是介面沒有用這個資訊——目前是平鋪列出。

**建議**
審圖介面**依投影片分組**顯示，標示「投影片 12 · 2 張」，讓使用者在原始脈絡下判斷。
一頁兩張圖最常見的兩種情況，分組後一眼就能分辨：

- 一張產品照 ＋ 一張 logo／裝飾 → 分類器多半已經正確分開，使用者只需確認
- 兩張都是可用素材（左右對比、多角度） → 兩張都留，讓稿件在不同段落各用一張

**待你決定**
同一頁的兩張圖，是否允許**同時出現在一篇稿子裡**？我建議允許，但插圖邏輯要避免
把它們排在相鄰段落（看起來會像重複）。這需要動 `mdformat.article` 的圖片配置邏輯。

### ④ 標題欄位

> **原文**：標題通常是已確認的或大方向已確認，可以加個欄位讓使用者填，並標記若不填寫
> 則自動生成。這邊提供一個參考，檔案 0410_NB 2025 Grey Days Campaign_Media Proposal_Final
> 裡面其實針對每個媒體是有設定切角的，不過不宜把這當通例，不是每個都會有。

**現況**
標題完全由模型生成，前台沒有任何欄位可以指定。

**建議**
產稿表單新增兩個**選填**欄位：

- **標題**——填了就逐字使用，留空標示「將自動生成」
- **切角／方向**——一句話描述這篇要打的角度

意見書最後那句提醒很重要：**不是每份簡報都有預設切角，不能當通例**。
所以做法是「抽取時若找得到就帶出來當預設值，找不到就留空」，
絕不能因為找不到就擋住流程或自己編一個。

**待你決定**
使用者填的標題要不要納入 `required_fact_values()`（即列入事實覆蓋率檢查，
確保潤稿不會把它改掉）？我建議要——之前就發生過自動潤稿把 KOL 名字整批刪掉的事故。

### ⑤ 檢索策略：從前台移除 ⚠

> **原文**：檢索策略：意思是指「要模仿哪個媒體的風格？」這個意義不大，直接選媒體即可是嗎

**⚠ 理由與實際不符，但結論仍然成立**

「檢索策略」和「要模仿哪個媒體」是**兩件不同的事**，表單上是兩個獨立欄位：

- 「要模仿哪個媒體的風格？」→ 選風格指南，決定文風
- 「檢索策略」→ 決定拿哪幾篇該媒體的舊文章當語感範例

所以意見書這裡是誤讀了。**但移除的結論我支持**，理由不同：

我們做過 81 篇、跨 4 份簡報與 5 位作者的三方比較（見《報告第一版.md》§4.7），
三種策略的產出**分不出差異**（評審分數全距 0.02）。既然使用者選什麼都一樣，
這個選項就只是增加認知負擔。

**建議**
前台移除該欄位，後台保留（研究時仍需要）。

**待你決定** —— 前台移除後，內部固定用哪一種？

| 選項 | 理由 |
|---|---|
| `typical`（你先前指定的預設） | 維持現狀，不改變任何已驗證的行為 |
| `none`（不放範例） | 品質實測相同，快約 20%、每篇省 14% 成本，且完全排除照抄範文的可能 |

從數據看 `none` 較有利，但這會改變產稿行為，我不想擅自決定。

### ⑥ 潤稿：固定一次，不給調

> **原文**：潤稿：直接潤一次提交直接點好了，若不滿意，讓他重新生成。

**現況**
`brief_detail.html:76-82` 是一個 0–3 的數字輸入框，配一段頗長的說明文字。

**建議**
前台移除欄位，固定 `max_rewrites=1`（本來就是預設值），後台保留可調。
連帶把那段說明文字也拿掉——使用者不需要知道實驗結論。

**補充一個誠實的但書**
潤稿讓評審分數上升 0.19，但那個數字**有循環論證的成分**：系統拿評審的批評去改寫，
再讓同一個評審評分，優化的正是被測量的東西。不經 LLM 的風格相似度只動了 0.003。

固定成一次是對的（成本可控、行為單純），但**目前沒有獨立證據證明潤稿改善了品質**。
要確認得靠人工評分，那是報告裡一直沒補上的缺口。這不影響本次改版，只是不要在
對外文件裡把 +0.19 當成潤稿的效益。

### ⑦ 取消大綱 ⚠

> **原文**：大綱：取消，立意很好但最好把使用者當成幼稚園，不要哪麼麻煩。

**⚠ 這裡必須區分兩件事，否則會改壞**

「大綱」在系統裡有兩個身分：

| | 是什麼 | 該不該取消 |
|---|---|---|
| **大綱確認步驟** | 前台勾選後停下來讓使用者看大綱、可編輯、確認後才續寫 | **取消** ✅ |
| **大綱生成階段** | 方案 B 管線的第 4 步（檢索→重排→整理筆記→**訂大綱**→寫正文） | **保留** ❌ 絕不能砍 |

意見書講的是前者。若誤把後者一起砍掉，方案 B 就退化成方案 A，
而實測方案 A 的結構完整度明顯較差（2.00 vs 2.75），且我們曾發現
沒有大綱時必提事實會漏掉三分之一（覆蓋率 0.647）。

**建議**
移除 `review_outline` 勾選框、`draft_outline` 檢視與 `pending` 狀態在前台的呈現。
`stop_after_outline` 參數保留在服務層，後台仍可使用。

**待你決定**
既有那些停在「待確認大綱」狀態的稿件怎麼處理？（可能有殘留資料）
我建議前台不再顯示該狀態，但不刪資料。

### ⑧ 生成改彈窗、多視窗並排比較

> **原文**：生成：就另一個彈窗吧，讓使用者若不滿意回原視窗直接再次生成，
> 然後一堆視窗讓他並排比較。

**現況 —— 這項的技術落差最大**

`portal/views.py:216` 的 `generate()` 是**同步**的：`run_generation(run)` 直接在
請求裡跑完才回應，整整 1.5–3 分鐘。目前靠「請不要關閉頁面」這句話撐著。

這個架構撐不起意見書的要求。要能「回原視窗再次生成」並開多個視窗並排，
就必須**同時跑多個生成**，而同步架構下每一個都會佔住一個工作執行緒，
開發伺服器很快就塞住。

**建議**

1. **生成改為非同步**：建立 `GenerationRun` 後立刻回應，實際生成丟到背景執行，
   前端輪詢 `status` 欄位。系統已經有 `pending / running / refining / done / failed`
   這套狀態，不需要新增資料結構。
2. **不用彈窗，用新分頁**。瀏覽器預設會擋 popup，而且彈窗無法並排比較。
   `target="_blank"` 開新分頁，使用者要並排就自己拉視窗——這正是意見書想要的效果。
3. **並排比較頁**：一次選多篇稿件，同頁多欄顯示。後台已有 `compare_drafts`
   可以參考。

**待你決定** —— 背景執行怎麼做？

| 做法 | 優點 | 缺點 |
|---|---|---|
| A. Python 執行緒（`threading`） | 不需要新增任何基礎設施，當天可完成 | 伺服器重啟時進行中的工作會遺失 |
| B. 正式的工作佇列（Celery／RQ ＋ Redis） | 穩定、可重試、可監控 | 要多跑一個 Redis 與 worker，部署複雜度上升 |

以目前的使用規模，我建議 **A**，並在 `GenerationRun` 加一個時間戳記，
讓超過 10 分鐘還停在 `running` 的自動標為失敗。若之後要多人同時使用再換 B。

**⚠ 成本提醒**
「不滿意就再生成」會直接放大 API 花費——每篇約 NT$ 7–8。
現在流程慢，本身就抑制了重複生成；改成一鍵重生後，用量可能成倍增加。
建議加上每人每日產稿次數上限，或至少在介面顯示已生成次數。

## 五、風險提醒

1. **第二階段是主要風險來源。** 「自由文字更正事實」若讓 LLM 直接改寫 facts，
   有可能把已確認的品牌名、型號改錯，而這些正是稿件必須逐字保留的內容。
   差異確認畫面不是加分項，是必要的防護。

2. **第三階段有一個容易踩的陷阱**，就是把大綱的「使用者確認步驟」與
   「管線生成階段」搞混。改完務必跑一次事實覆蓋率回歸測試。

3. **第一階段會改變成本結構。** 目前的慢是天然的節流閥；改成一鍵重生後，
   每次點擊都是實際支出。
