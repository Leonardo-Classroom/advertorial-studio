# 第一版改進計畫

> 對應《第一版改進建議.md》的逐項分析。這裡只寫決定要怎麼做。

---

## 1 + 2：待確認事項與抽出的內容 —— 合成同一塊

①② 是同一個功能的兩個入口，不拆開做。`uncertain` 本身就是 facts 的一個欄位，
使用者回答問題、和使用者主動指出哪裡錯了，寫回去的位置是同一包資料、走同一條路徑：

    自由文字 → LLM → 更新後的 facts → 新版本

**只給一個輸入框**，不做兩個。兩個框會產生使用者無法回答的問題（「我要改的東西剛好也是
系統在問的，該打在哪一格？」），而且兩個入口都能寫 facts，版本就不是一條線——A 框送出
產生 v2 時 B 框裡還留著打到一半的字，那次更新要以 v1 還是 v2 為基礎？

但 ① 要成立，靠的是**編號清單與輸入框相鄰**——編號在眼前，才會自然打出「1. …／2. …」。
所以把待確認清單從頁面最上方搬進「抽出的內容」卡片，放在敘述上方、輸入框同一張卡裡。

### 版面

```
┌─ 抽出的內容        檢視版本 [v2 ▾] ─┐   ┌─ 產出廣編稿 ────────────────┐
│  ⚠ 這幾處系統不確定，請你確認：      │   │  以哪一版產稿 [v2 ▾]        │
│     1. 合作 KOL 是「陳○○」還是…？   │   │  ⚠ 還有 2 處系統不確定      │
│     2. 活動日期只寫了「9 月」        │   │                             │
│                                      │   │  要模仿哪個媒體的風格？     │
│  【品牌】…                           │   │  [ ▾ ]                      │
│  【產品】…                           │   │                             │
│  【必提詞】…                          │   │  [ 產出廣編稿 ]             │
│  ─────────────────────               │   └─────────────────────────────┘
│  要更正什麼？（可直接用 1. 2. 回答）  │
│  ┌──────────────────┐  [更新]        │
└──────────────────────────────────────┘
```

兩個下拉選單意義不同，標籤必須分開寫（「檢視版本」／「以哪一版產稿」），
否則使用者會以為是同一個控制項壞掉了——改左邊右邊沒動。

### 做法

- 待確認清單加數字編號，移進卡片內、敘述上方。
- facts 前台改成分區塊的可讀敘述（md 格式）：品牌、產品、必提詞、合作人選、活動資訊…
  `internal_only` 整段不顯示——反正系統本來就不會把它寫進稿子。
- 移除 JSON 編輯框，改唯讀敘述。**後台維持 JSON 編輯**，那是管理者除錯用的。
- 移除「只儲存」「確認無誤」按鈕，改成「要更正什麼？」文字輸入框 ＋「更新」按鈕，
  讓使用者用自然語言編輯。問題的回答和自發的更正混在同一段文字裡沒關係，
  對 LLM 來說本來就是同一件事，不需要先幫它分類。
- 「抽出的內容」標題右側加「檢視版本」下拉，預設最新版，每次按「更新」產生新版本。
- 更新後**直接存成新版本**，不中途攔一個確認頁。決策 B 原本把前後對照列為必要防護，
  但那是在沒有版本概念的前提下想的：現在什麼都不會被覆蓋，合併壞了就切回上一版產稿，
  而更正多半只是改一個名字，為此插一個確認頁比它想防的錯誤更煩人。
  前後對照的畫面仍然做好放著，由後台高級分頁的「更正事實前先確認差異」開關控制，
  預設關閉——若日後真的出現「模型把沒提到的欄位一起改掉」，打開即可。

## 版本取代「確認無誤」

**前台不再有 `confirmed` 狀態。** 那個按鈕本來就沒有承載資訊——按下去不代表使用者
真的核對過，只是被擋住所以按了。改成：v1 一產生就能產稿，使用者選哪一版就用哪一版。
不滿意就更新出 v2、v3，選擇本身即是確認。

- 產稿卡片自己一個「以哪一版產稿」下拉，**預設最新版**。
- **`GenerationRun` 必須記錄實際採用的版本。** 這是硬需求：⑧ 的並排比較上線後，
  兩篇稿子不同時，必須能分辨是風格／重生造成的，還是根本用了不同的事實。
  沒有這個欄位，比較頁得到的結論都不可信。
- 事實覆蓋率檢查改成對照該次採用的版本，不能再讀 `Brief.facts`。
- 待確認事項**不擋產稿**，但產稿卡片顯示一行「還有 2 處系統不確定」。
  他要無視就直接按下去，但不是不知情。
- 小項待定：步驟條的「步驟 2 核對抽出的內容 ✓」失去打勾的觸發點，
  改成進頁面即為進行中、產稿後才推進到步驟 3。

### 資料結構

新增 `BriefFacts`：

| 欄位 | 說明 |
|---|---|
| `brief` | FK |
| `version` | v1, v2, … |
| `data` | 該版的 facts |
| `source` | `extract`（上傳時抽取）／`user_update`（使用者更正） |
| `user_input` | 使用者當時打的那段自由文字 |
| `created_at` | |

`Brief.facts` 退成「取最新版」的捷徑，`GenerationRun` 加 FK 指向實際採用的那版。
`user_input` 一定要存——日後要檢討 LLM 合併把什麼改壞了，那是唯一的證據。

## 移除「重新讀取」，失敗一律在上傳頁解決

使用者可以直接用自然語言更新，前台不需要重抽按鈕。**後台也不留**，後台頂多讓管理者看資料。

但現在 `portal/views.py:107-124` 兩條失敗路徑都是 redirect 進詳情頁、再叫使用者按
「重新讀取」重試。按鈕拿掉，失敗處理就必須搬回上傳頁——這是配套，不是額外工作。

| 失敗 | 現況 | 改成 |
|---|---|---|
| `extract_text` 失敗（簡報讀不開、檔案損毀） | 進詳情頁顯示錯誤 | **停在上傳頁**，提示「檔案讀不開，請確認後重新上傳」 |
| `extract_facts` 失敗（模型逾時、回傳格式錯誤） | 進詳情頁顯示警告，叫使用者按重新讀取 | **停在上傳頁**，顯示「系統忙碌，讀取內容失敗」＋「再試一次」按鈕，用剛才那個檔案重跑抽取 |

模型失敗時給「再試一次」而不是要求重新上傳：檔案是好的、投影片也解析完了，
重傳等於把沒問題的解析再跑一遍，大檔案還要重新上傳一次。位置仍在上傳頁，
不進詳情頁——失敗在哪裡發生就在哪裡解決。

失敗時不要留下半殘的 Brief 紀錄在「我的稿件」列表裡。

**明確不做**：抽取「沒報錯但結果幾乎空白」的檢查。相信模型，不為這種情況加防呆。

## 附帶效果

更新後產生 v2 時，已經答完的項目就從待確認清單消失。清單變短本身就是進度指示，
不必另外做確認 UI。這只有在「清單與輸入框屬於同一個版本快照」時才成立，
兩個框各自送出做不到——這也是合成一個的另一個理由。

## 5 + 6 + 7：表單簡化 —— 前台不問，預設值搬進後台高級分頁

三項都是「使用者不需要面對的旋鈕」。共同做法：**前後台的表單欄位都移除，
`GenerationRun` 的欄位與服務層邏輯一行不動**，預設值改由後台高級分頁設定。

研究能力不受影響——81 次的三方比較是走 `run_experiment` 管理指令跑的
（`studio/management/commands/run_experiment.py:147`），不是靠後台表單。

### ⑤ 檢索策略

- 前台、後台產稿表單都移除該欄位。
- **`GenerationRun.retrieval_strategy` 欄位不能刪**——後台的策略比較統計頁
  （`studio/views.py:286-320`）整頁靠它。
- 預設維持 `typical`。

決策 4（`typical` vs `none`）不必現在定。實測三種策略品質分不出差異（評審分數全距 0.02），
`none` 快約 20%、每篇省 14%。有了高級分頁，之後改一個設定值就能實測，不用改程式。

### ⑥ 生成評估後重寫次數

- 前台、後台表單都移除，連同那段說明實驗結論的文字一起拿掉——使用者不需要知道。
- **不寫死在程式裡**，放進高級分頁，預設 1。寫死的話 `run_experiment` 就不能變動它做實驗，
  而放進高級分頁對使用者而言效果相同：前後台都看不到。

### ⑦ 大綱確認步驟

`stop_after_outline`（`studio/services/pipeline.py:49,124`）是管線的**提前中止點**，
跟第 4 步的**大綱生成階段**本來就是分開的兩件事——前端不勾，就等於永遠不中止。

- 移除 `portal` 與 `studio` 兩邊的「先讓我確認大綱」勾選框，服務層一行不動。
- 前台不再顯示「待確認大綱」狀態與大綱檢視畫面。
- 既有停在該狀態的稿件：**前台不顯示，但不刪資料**（本機可能有殘留）。

**回歸測試（必做）**：改完跑一次事實覆蓋率，須維持 1.000。這是第三階段最容易踩的坑——
若誤把大綱生成階段一起砍掉，方案 B 會退化成方案 A，結構完整度掉到 2.00（vs 2.75），
且曾實測必提事實會漏掉三分之一（覆蓋率 0.647）。

## 後台「高級」分頁

用來設定產稿參數的預設值，取代前台那些旋鈕。

| 設定 | 預設 |
|---|---|
| 檢索策略 | `typical` |
| 生成評估後重寫次數 | 1 |
| 範例篇數 | 4 |
| 更正事實前先確認差異 | 關閉 |

**模型與金鑰留在 `.env`**（`LLM_MODEL`、`LLM_JUDGE_MODEL`…），不進高級分頁。那是部署層級的
東西，不該讓人在網頁上改；評審模型尤其不能隨手換——換了整批評分就不可比。

- 實作：單例模型 `SiteSettings`，Django admin 可直接編輯，改完立即生效不必重啟。
- **設定只是「建立 run 時的預設值」，實際值仍複製進 `GenerationRun`**
  （現有行為，`studio/models.py:76-79` 已經這樣存）。這樣改了預設，舊紀錄仍知道自己
  當時用什麼——跟 facts 版本 FK 同一個道理。
