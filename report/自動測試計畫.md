# 自動測試計畫

> 建立於 2026-08-09。四項任務循序執行，每項完成後在 `report/` 產出一份獨立報告。
> 本文件是總綱與方法論；實際數據與發現寫在各任務報告裡。

---

## 執行環境現況（開工前實測）

| 項目 | 值 |
|---|---|
| 產稿後端 | **本地**（`SiteSettings.llm_backend = local`） |
| 文字模型 | `qwen3.6:27b-q4_K_M` |
| 視覺模型 | `qwen3-vl:8b` |
| 嵌入模型 | `BAAI/bge-m3`（本地，與上兩者共用同一張 4090） |
| 並行上限 | `max_parallel_runs = 2` |
| 預設方案 | `single`（方案 A） |
| 帳號 | `admin`（staff／superuser）、`demo`（一般） |
| 測試檔案 | `測試文件/` 下 pptx(124MB)＋pdf(990KB)＋docx(4.3MB)，共 3 檔 |
| 服務 | dev server（:5860）運行中、Ollama（:11434）運行中 |
| 磁碟 | 剩 275.5 GB |
| 程式規模 | 10,772 行 Python（不含 migrations／datasets） |

**單一 GPU 的根本限制**：文字、視覺、嵌入三個模型輪流換入換出同一張 24GB 卡。
不論開多少執行緒，模型層都是**序列化**的。報告 §4.2 記錄本地文字生成約 20% 機率
耗時拉長 5～50 倍、圖片辨識約 30% 機率失敗或空白——任務三、四必須把這些
失敗模式當成正常觀測項，而非意外。

## 任務一：系統全面檢查（bug／漏洞／使用邏輯）

**性質**：靜態程式碼審查 + 針對性動態驗證。無需 GPU，可立即執行。

**範圍**：跨 `accounts / briefs / corpus / portal / studio / core` 六個 app。重點面向——

1. **正確性 bug**：邊界條件、None 處理、race condition、交易一致性、
   查詢集在迭代中被修改、`select_related`/`annotate` 的欄位衝突（本 session 撞過）。
2. **資料一致性**：`Brief.facts` 鏡像與版本列的同步、`processing` 旗標的清理路徑、
   多檔案上傳的合併去重、版本編號的連續性。
3. **使用邏輯設計**：前後台資料範圍的落差、失敗狀態的可見性、
   同一份資料在不同頁面顯示不一致、無法回退的操作。
4. **背景執行緒的健全性**：daemon thread 死亡時的收尾、`reap_stale` 的涵蓋範圍、
   `connections.close_all()` 的正確性。
5. **效能陷阱**：N+1 查詢、深分頁、缺索引、在請求內做重運算。

**方法**：逐 app 精讀，可疑處以 `manage.py shell` 實測復現。每個發現標註
嚴重度（高／中／低）、觸發條件、影響、與修法建議。

**產出**：`report/任務一_系統檢查報告.md`

## 任務二：資安檢查與滲透測試

**性質**：對自有系統的授權滲透測試。針對 dev server 實際發動，非破壞性為原則。

**範圍**——

1. **認證與授權邊界**：未登入可及的端點、`@login_required`/`@staff_required`
   的涵蓋、前台 view 是否一律以 `owner=request.user` 過濾。
2. **IDOR（越權存取）**：能否用他人的 `brief_id`/`run_id`/`guide_id` 存取或修改
   不屬於自己的資源——逐一測試 portal 的每個 `<int:pk>` 端點。
3. **CSRF**：fetch 端點（改名、開關、圖片核准、圖說儲存）的 token 驗證。
4. **注入**：`icontains` 搜尋、檔名、圖說、專案名稱、自然語言更正——
   SQL 注入（Django ORM 應免疫，但驗證 raw 查詢）、模板注入、
   儲存型 XSS（圖說會不會 escape、`mark_safe` 的使用是否安全）。
5. **檔案上傳**：格式偽裝（副檔名 vs 內容）、超大檔、zip bomb 式的惡意 pptx、
   路徑穿越（檔名含 `../`）。
6. **登入狀態下的惡意操作**：竄改隱藏欄位（`base_version`、`facts_version`、
   `style_guide`、繞過必填）、以停用的 guide 產稿、越權改別人的專案名稱。
7. **排程 DoS**：一個登入使用者能否用連續／並發的產稿請求塞爆排程佇列、
   耗盡執行緒、撐爆 SQLite 寫入鎖、或讓 `max_parallel_runs` 閘門失效。
   （與任務三的排程觀測互補：這裡從對抗角度，任務三從真實負載角度。）

**方法**：Django test client（含 `enforce_csrf_checks`）+ 直接 HTTP。
每個嘗試記錄：攻擊手法、預期、實際結果、是否成功、修法。

**產出**：`report/任務二_資安檢查報告.md`

## 任務三：壓力測試（5 使用者並發）

**性質**：真實端對端負載測試，重度 GPU，預估**數小時**（見下方風險）。

**設計**：
- 建立 5 個 test 帳號（`stress1`～`stress5`）。
- 每個帳號用 `測試文件/` 的三個檔案建 5 個專案 → 共 **25 個專案**。
- 每個專案：上傳解析 → 抽取事實 → 圖片辨識（勾選 5～10 張）→ 產出廣編稿。
- 5 個帳號的作業**同時**發動，觀察排程行為。

**要記錄的時間**（每個專案、每個階段）：
- 上傳→解析完成、事實抽取起訖、圖片辨識起訖（含每張）、
  產稿排隊時間（`created_at`→`started_at`）、產稿各階段（`stages[].elapsed_ms`）、
  總 `elapsed_ms`。

**要觀察的排程現象**：
- `max_parallel_runs=2` 閘門是否確實限制並發、佇列深度隨時間變化、
  SQLite 寫入鎖競爭、記憶體／VRAM 換入換出的代價、
  失敗率（文字 ~20%／圖片 ~30%）與失敗如何影響後續排隊、
  是否出現 `processing` 卡死、daemon thread 是否有洩漏。

**方法**：直接呼叫 service 層（`upload.create_brief`、`ingest_runner`、
`images.classify_checked`、`runner.submit`）在多執行緒中模擬並發，
以背景程序執行並定期輪詢快照，全程寫入結構化 log。

**產出**：`report/任務三_壓力測試報告.md`

## 任務四：A/B 方案速度比較

**性質**：受控的方案 A（single）vs 方案 B（staged）速度對照，中度 GPU。

**設計**：
- 用**單一** test 帳號，`測試文件/` 建 5 個專案（含圖片辨識，勾 5～10 張）。
- 每個專案分別以方案 A、方案 B 各產一輪 → 共 **10 次產稿**。
- 兩方案跑在同一份專案／同一版事實／同一風格指南上，唯一變因是 `mode`。

**要記錄的細節時間**：
- 方案 A：單次生成的總時與（若有）自動重寫時間。
- 方案 B：逐階段——① 檢索範文 ② 依文體重排 ③ 整理重點筆記
  ④ 訂大綱 ⑤ 寫正文 ⑥ 依評審重寫，每階段的 `elapsed_ms`。
- 排隊時間、每個專案兩方案的差值、5 個專案的中位數與全距。

**基準對照**：既有 `report/本地線上API比較.md` §四記錄方案 A 中位 31.1s、
方案 B 中位 104.2s（皆本地、無圖片流程）。本次含圖片辨識且為三檔案專案，
數據會不同，報告需說明差異來源。

**方法**：沿用既有 `manage.py run_experiment`（本就為 A/B 比較設計、
會記錄逐階段時間），或直接以 service 層受控執行。

**產出**：`report/任務四_AB方案比較報告.md`

## 關鍵風險與待確認事項

1. **任務三、四的後端與時間預算**。本地後端下，任務三的 25 個專案（每個含
   事實抽取 ~2 分＋圖片辨識 5～10 張 ~2-4 分＋產稿 ~0.5-2 分）在單 GPU 序列化下
   估計 **4～8 小時**，且會反覆撞到 20-30% 的失敗率；任務四約 **1～2 小時**。
   線上後端會快很多且穩定，但花 API 額度、且測不到本地路徑。

2. **執行順序**：任務一、二不需 GPU 可先做完；任務三、四是長時間 GPU 作業，
   建議確認參數後再啟動（可背景執行）。

3. **測試資料清理**：任務三會產生 25 個專案 + 大量 run + 3GB＋媒體檔。
   需確認測後是否保留（供你檢視）或自動清除。

## 決策定案（2026-08-09）

- **後端**：任務三、四皆用**本地**（qwen3.6:27b + qwen3-vl:8b），測真實部署路徑，
  失敗與降速當觀測項。
- **節奏**：四項**全自動連續執行**，每項完成產一份報告，中途不停下確認。
  重度 GPU 任務（三、四）以背景程序執行。
- **測試資料**：**保留供檢視**，報告附上一鍵清除指令。

執行順序：任務一（靜態審查）→ 任務二（滲透測試）→ 任務三（壓力測試，背景）
→ 任務四（A/B 比較，背景）。
