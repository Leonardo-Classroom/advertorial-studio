沒有選任何一列時，線上後端沿用 .env 的 LLM_BASE_URL / LLM_API_KEY / LLM_MODEL。金鑰存在資料庫裡， 能讀到資料庫或其備份的人就拿得到——要作廢請到供應商後台換金鑰。

評審也跟著這個設定切換。選線上時評審是另一個模型 （LLM_JUDGE_MODEL）；選本地時，這張卡上只有一個文字模型， 所以寫稿的和評分的是同一個模型。這種情況下的絕對分數意義不大 ——模型評自己寫的東西——但 A/B 這類相對比較仍然可用，因為兩邊 由同一個評審、且成對比較會左右對調各評一次。每筆評分都會記下當時的評分模型， 看分數時不必猜是誰評的。

嵌入模型（BGE-M3）跑在 GPU 還是 CPU。它由本程式直接載入、佔約 2.3GB VRAM，且不受下面「閒置卸載」控管。在單張 24GB 卡上， 文字模型載入後就佔 18.2GB、Windows 主機另外佔約 2.5GB，只剩 3.8GB； 嵌入模型若也放 GPU，餘裕只剩 1.5GB，逼近 Ollama 開始把層數丟回 CPU 的邊緣。 改用 CPU 可騰出這 2.3GB，代價是查詢時嵌入慢約 44 毫秒 （在數十秒的產稿旁看不出來），只有「重建整個語料索引」這種批次作業會明顯 變慢（實測約 11 倍）。注意：這不會讓文字與圖片模型同時常駐 ——兩者載入後共需 28.4GB，這張卡上必定互相踢出。 只有在上面選「本地模型」且 .env 的 EMBED_BACKEND=local 時才有作用。改動會立即重載模型。

本地文字／圖片模型在最後一次使用後，閒置這麼多分鐘就從 VRAM 卸載 （透過 Ollama 的 keep_alive）。作業期間反覆使用會一直 重設計時、保持暖機；沒人用時才釋放 VRAM。預設 3。 設 0 = 用完立即卸載，之後每次都要重新載入（換一次模型實測約 6～9 秒， 壓測時的極端冷啟動可達 12 倍慢），不建議。 只影響本地模型，線上 API 不受影響。

決定拿哪幾篇該媒體的舊文章當語感範例。實測 81 篇、跨 4 份簡報與 5 位作者， 三種策略產出分不出差異（評審分數全距 0.02）。 「不放範例」品質相同、快約 20%、每篇省 14% 成本，且完全排除照抄範文的可能。

產稿在背景執行緒跑，使用者可以連按好幾次。超過上限的會排隊，不會同時打出去—— 調高會加快多篇產出，也會同時放大 API 用量與 SQLite 的寫入競爭。

右邊那個管的是不同的事：同時可以打給本地模型的請求數， 產稿、圖片辨識、抽取內容全部算在內。Ollama 一次只跑一個推論 （27B 在這張卡上就是 1），排不上的請求會在它那邊等到逾時——壓力測試實測 5 人同時上傳時，96% 的內容抽取因此逾時失敗。這個閘門把等待 留在我們這邊（等待免費），而不是留在 Ollama 那邊（等待會吃掉請求的逾時額度）。 只在後端為本地模型時生效。

0 = 只寫初稿；1（預設）= 寫完後依評審意見自動潤一次。 本地後端實測（任務四重跑，方案 A）：不潤約 31 秒、潤一次約 86 秒 ——潤稿本身要 50-55 秒，因為它包含一次完整的評審呼叫，是兩個方案共同的固定成本。 實測第 2 次重寫 12 篇中 0 篇被採納。重寫若造成事實流失或分數沒提升會自動停止並保留前一版。
潤稿讓評審分數上升 0.19，但那個數字有循環論證的成分——系統拿評審的批評去改寫， 再讓同一個評審評分。不經 LLM 的風格相似度只動了 0.003，目前沒有獨立證據證明潤稿改善了品質。

模型逾時

單次呼叫超過這個秒數就放棄並標記失敗。本地模型偶爾會停不下來，這是唯一 能讓它乾淨結束的機制。三個數字分別對應三種工作，同一種工作的所有呼叫共用 一個值。

參考實測值：產稿暖機後約 50 秒、冷啟動可達數百秒；單張圖片 13–28 秒； 三檔案專案（約 2 萬字）的內容抽取暖機後約 45 秒。
調高不會讓模型變快，只是讓它有更多時間；真正要看的是失敗訊息說的是 「超過 N 秒沒有回應完畢」（該調高）還是「排不到本地模型」（該調的是上面的 同時呼叫上限）。「卡住多久算死掉」會自動跟著這些數字調整， 不必也不能另外設定——那兩個值若配得不一致，健康的工作會被當成死掉而誤殺。

上傳限制

檔案上傳沒有內建上限——Django 只限制表單欄位，檔案是直接串流到磁碟。 不設限的話，一個登入的使用者可以一份份簡報把磁碟塞滿。這幾個上限在建立 專案之前就檢查，被擋下的上傳不會留下任何東西。

目前見過最大的真實簡報是 124MB，所以單檔預設 200 留有餘裕。 合計上限擋的是「每個檔都合格、但一次丟二十個」。

.pptx 與 .docx 本身就是 zip 壓縮檔（Office 2007 起的格式，副檔名的 x 就是這個意思），抽圖時必須解開。 所以除了「檔案多大」，還要管「解開後會變多大」——壓縮炸彈可以 只有 1MB、解開後好幾 GB。正常簡報的壓縮比約 1:1（裡面的圖片 早就壓過了，實測 119MB 那份是 1.09:1），所以 200:1 對正常檔案有極大餘裕。 這項檢查只讀 zip 目錄裡宣稱的大小、不做解壓，成本為零；宣稱值是造檔者寫的， 所以真正不依賴它的後盾是上面的單檔上限。

後台導覽

只是收起導覽連結，網址仍然進得去，也不影響任何權限。 這兩頁與前台的差別在於範圍：後台看得到所有使用者的資料， 前台只看得到自己的；失敗的稿件也只有後台列得出來。

不在這裡的東西

線上模型的端點與金鑰現在設在上面的清單裡，不再只能改 .env——沒有設定任何一列時才回頭用 .env。 本地模型仍設在 .env （LOCAL_LLM_MODEL、LOCAL_LLM_VISION_MODEL）， 因為那綁著這台機器裝了什麼。評審模型不能隨手換——換了之後整批評分就不可比； 每筆評分都記著當時用的模型，比較前先確認是同一個。
要掃不同參數組合請用 python manage.py run_experiment， 它可以逐一變動策略與重寫次數，不受這裡的預設值限制。
這裡的設定只在建立生成紀錄的當下被複製進該筆紀錄，改了不會影響任何既有稿件。
